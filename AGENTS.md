# AGENTS.md

This file provides guidance to Codex (Codex.ai/code) when working with code in this repository.

## Project Overview

Novel Vibe is a multi-agent web novel generation system. Users interact with a Chief Editor agent that coordinates 6 specialized sub-agents (Worldbuilder, Character Designer, Outliner, Chapter Director, Chapter Writer, Script Supervisor) to collaboratively produce novels. All novel content is stored as Markdown files with YAML frontmatter in InsForge Storage (S3), with frontmatter indexed in PostgreSQL.

## Commands

```bash
# Start all services (InsForge Docker + Agent Server + Web BFF + native WebUI)
npm start
./scripts/start.sh                  # All services (macOS only)
./scripts/start.sh --infra-only     # InsForge Docker only
./scripts/start.sh --agent-only     # Agent server only

# Stop application services (does not stop Docker by default)
npm stop

# Run agent server directly
npm run agent                       # → http://localhost:7140

# Run Web BFF / native browser WebUI directly
npm run web                         # → http://localhost:9120
npm run webui:new                   # → http://localhost:5173

# Run the connected Tauri 2 desktop shell (requires a Rust toolchain)
npm run desktop:dev                 # loads the configured WebUI origin
npm run desktop:make                # create local platform installers (dmg / NSIS)

# Within packages/novel-agents/
npm run dev                         # tsx watch mode
npm run build                       # tsc
npm run test                        # vitest
npm run check                       # typecheck + test with coverage (one-shot)
```

## Verification

```bash
# CI order: typecheck first, then test. Both must pass.
npm run check:agents                # typecheck + test (packages/novel-agents)
npm run check:web                   # typecheck + test (packages/novel-web)
npm run check:webui                 # typecheck + test (packages/novel-webui)
npm run check:desktop               # cargo fmt + clippy + tests (packages/novel-desktop, Rust)
npm run check                       # production chain, including desktop

# E2E (requires all services running)
npm run test:e2e                    # quick checks (no LLM)
npm run test:e2e:full               # full test including agent chat
```

Coverage thresholds (vitest.config.ts): statements 70%, branches 65%, functions 75%, lines 70%.

There is no linter (eslint) for `packages/novel-agents/`. Only typecheck + vitest. InsForge has its own eslint config.

## Hosted Operations

Running the hosted service — deployment, server access, the admin dashboard tunnel, TLS
certificates and release promotion — is an operator concern. That runbook lives in the private
ops repository, and nothing in this repository depends on it. Self-hosters follow the local
development flow in `docs/development-workflow.md` plus the `nginx/` configs.

## Repository Structure

This repository contains five custom application packages plus separately managed runtime dependencies:

- `packages/novel-agents/` — **Custom code**: agent definitions, tools, and internal HTTP/SSE server
- `packages/novel-web/` — **Custom code**: browser BFF for login/session cookies and HTTP/SSE proxying
- `packages/novel-webui/` — **Custom code**: native browser React WebUI used for production
- `packages/novel-desktop/` — **Custom code**: connected Tauri 2 desktop shell (Rust), injected capability bridge, packaging, and updater
- `packages/novel-mcp/` — **Custom code**: remote MCP adapter for API-token authentication, scoped tools, and Agent chat access
- `InsForge/` — Backend-as-a-service (Docker): PostgreSQL, Storage (S3), Auth, AI Gateway
- `@earendil-works/pi-agent-core` / `@earendil-works/pi-ai` — Agent runtime installed from npm
- `Memori/` — Agent session memory (Python, per-agent process_id)
- `webui-dist/` — Prebuilt output of `packages/novel-webui`, generated by `make build-webui-dist` and served by nginx. The open-source tree does not commit it; the hosted deployment ships the generated artifact from the private ops repository. See "WebUI Build and Deployment Boundary" below.

The dependency projects are in `.gitignore` and managed separately: `InsForge/` is cloned by
`make setup` from the public fork (`https://github.com/encyc/novel-vibe-insforge.git`; override with
`INSFORGE_REPO_URL` — see `docs/self-hosting.md`), and the rest have their own git repos. Custom
application code lives in the five `packages/novel-*` directories listed above.

## Architecture

### Agent System (packages/novel-agents/)

The package has one executable service entrypoint:

- `server.ts` — Starts the Agent HTTP/SSE server and constructs the live orchestrator.
- `agents.ts` — Defines `NovelOrchestrator` and creates live pi Agent instances with sub-agent delegation. The `delegate_to_agent` tool on the Chief Editor invokes sub-agent `.prompt()` directly.

The runtime shares the tools (`tools/`), prompts (`prompts/`), and libs (`lib/`). There is no separate static Agent registration entrypoint.

### Tool Architecture

All tools follow a factory pattern: `createXxxTools(ctx: ToolContext)` returns `AgentTool[]`. The `ToolContext` holds a `StorageClient`, `DbClient`, and `projectId`. Tools are assigned to agents by config in `agents.ts` via the `file`, `index`, `status`, `delegate`, `skill`, `web`, and `interaction` tool sets.

### Document Storage: Markdown First, DB Index Second

- Content: Markdown with YAML frontmatter in InsForge Storage (`novels/{project_id}/...`)
- Index: Frontmatter parsed by `lib/frontmatter.ts` and upserted to `document_index` table via `sync_index` tool
- The DB index is a denormalized cache; the Markdown files in S3 are the source of truth
- `lib/db.ts` is a facade: `DbClient` keeps connection plumbing (token lifecycle, headers) and its public API; domain queries live in `lib/db/<domain>.ts` as functions receiving the `DbRequestContext` implemented by `DbClient`. New DB queries go in the domain module, with a one-line delegation on the class.

### Frontmatter Schema

All document types and their frontmatter schemas are defined in `schemas/frontmatter.ts` using `@sinclair/typebox`. Document types: `worldview`, `character`, `relationships`, `volume`, `chapter-skeleton`, `chapter-card`, `director-script`, `chapter-text`, `foreshadow`, `story-summary`, `character-state`.

Document status lifecycle: `draft` → `confirmed` → `locked`. Only the Chief Editor changes status based on user approval.

### Server and Web BFF

- `server.ts` — HTTP server with SSE streaming. Routes:
  - `POST /api/chat` — Chat with Chief Editor
  - `GET/POST /api/projects/:id/sessions` — List/create durable Chief Editor Sessions
  - `GET /api/sessions/:id/messages` — Read cursor-paginated display messages
  - `PATCH /api/sessions/:id` — Open or rename a Session
  - `DELETE /api/sessions/:id` — Strong-delete a Session and its project-memory references
  - `POST /api/projects` — Create project
  - `GET /api/documents/:pid` — List documents (optional `?type=` filter)
  - `GET /api/documents/:pid/*` — Read document content
  - `PUT /api/documents/:pid/*` — Write document + sync DB index
  - `DELETE /api/documents/:pid/*` — Delete document + clean DB index (including foreshadow cleanup)
  - `GET /api/projects/:id` — Get project info

  `server.ts` is only the dispatcher: the route tables live in `server/router.ts` (`AUTH_ROUTES` order preserves original precedence), handlers live in `server/routes/<domain>.ts`, shared HTTP helpers and `RouteContext` in `server/http.ts`, and per-request service factories in `server/runtime.ts`. New routes are added to the tables, not to `handleRequest`.

- `packages/novel-web` — HTTP BFF for browser sessions. It authenticates against InsForge, stores the InsForge access token server-side in an opaque cookie session, and proxies `/api/projects`, `/api/documents/*`, and `/api/chat/stream` to the agent server.

### Durable Chief Editor Sessions

PostgreSQL is the source of truth for exact conversation history. `novel.sessions` stores Session metadata and processing leases, `novel.session_messages` stores complete pi messages and display status, and `novel.session_agent_state` stores per-agent compaction summaries. The Agent Server may cache active orchestrators, but every one of the seven agent transcripts can be restored from summaries plus exact messages after a process restart.

Each chat turn acquires an atomic Session lease, persists the user message and assistant placeholder before generation, streams only Chief Editor display events, then completes or marks the placeholder failed. A disconnected browser does not cancel server-side generation. Context compaction is performed independently for all seven agents; summary model usage is recorded through the same credit billing path as ordinary agent calls.

Project memory is asynchronous and durable. `novel.memory_jobs` is claimed with `FOR UPDATE SKIP LOCKED`, retried with backoff, and processed by the Agent Server memory worker. `novel.memory_exclusions` prevents deleted Session memories from being recalled. Strong Session deletion refuses indeterminate memory enumeration, records exclusions before deleting exact history, and cancels pending capture jobs.

The browser accesses Session routes only through the Web BFF, which overwrites any supplied `user_id` with the authenticated cookie identity. Durable novel Sessions do not change the BFF login-session scope: login cookies remain server-memory-backed and surviving a BFF process restart is intentionally out of scope.

### Nginx Routing (Production)

nginx proxies `/api/`, `/health`, and `/login` to the Web BFF (port 9120). Static WebUI files are served directly from `webui-dist/`. The agent server (7140) is never directly exposed to the browser.

### Frontend ↔ Backend Communication Flow

The production browser UI communicates with our backend through a simple HTTP/SSE chain:

```
packages/novel-webui
  → fetch("/api/*", same-origin cookies)
      │
      ▼
packages/novel-web (:9120)
  → server-side InsForge access token
      │
      ▼
packages/novel-agents/server.ts (:7140)
  → StorageClient / DbClient
      │
      ▼
InsForge (S3 + PostgreSQL)
```

**webui-dist rebuild**: After changing `packages/novel-webui`, run `make build-webui-dist` from the repo root. This builds `packages/novel-webui`, syncs `packages/novel-webui/dist/` into `webui-dist/`, and preserves PWA-only assets.

### WebUI Ownership

生产 WebUI 是独立的 `packages/novel-webui`。新增浏览器 UI 功能时，代码写在 `packages/novel-webui/src/` 下，并通过 `packages/novel-web` 的认证边界访问后端。

### Desktop Ownership

`packages/novel-desktop` is a connected shell around the production WebUI. It must not contain Agent, Session, billing, document, storage, or other product business logic; those capabilities remain behind the Web BFF and Agent Server.

Features shared by browser and desktop belong in `packages/novel-webui`. Desktop-only native features must be exposed through the narrow, versioned `window.novelDesktop` bridge injected by the shell. The WebUI must feature-detect bridge capabilities and keep a browser-safe fallback; do not fork the frontend into a desktop copy.

### WebUI Build and Deployment Boundary

The browser WebUI reaches servers as a **prebuilt artifact**; the server does not compile it.

1. Build it from this repository: `make build-webui-dist` runs the `packages/novel-webui` build and
   syncs `packages/novel-webui/dist/` into `webui-dist/`.
2. PWA assets survive that sync: `manifest.json`, `favicon.ico`, `favicon.svg`,
   `apple-touch-icon.png`, `icon-192.png` and `icon-512.png` are copied across.
3. Serve `webui-dist/` with nginx (routing contract in `nginx/templates/`, generic base config in
   `nginx/nginx.conf`). The artifact must carry
   `<meta name="novel-vibe-webui" content="native">` in `index.html`; the hosted release preflight
   rejects an artifact without it, and desktop-only runtime markers are rejected as well.
4. `login.html` no longer exists — `/login` is an SPA route handled by the Web BFF.

`webui-dist/` is generated build output rather than source, and the published open-source tree does
not carry it: the hosted deployment keeps the artifact on the operator side, while a self-hoster
runs step 1 and points nginx at the result — see `docs/self-hosting.md`.

### Document Management (CRUD)

Documents are managed through four layers — each with read, write, and delete operations:

| Layer | Read | Write (save) | Delete |
|-------|------|-------------|--------|
| StorageClient | `read(path)` | `write(path, content)` | `delete(path)` |
| DbClient | `listDocuments()` / `getDocument()` | `upsertDocumentIndex()` | `deleteDocument()` + `deleteForeshadow()` |
| Agent Tools | `read_doc` | `write_doc` (auto-syncs index) | `delete_doc` (cleans storage + DB + foreshadow) |
| HTTP API | `GET /api/documents/:pid/*` | `PUT` (writes + indexes) | `DELETE` (with ownership check) |

`write_doc` (Agent tool) was enhanced to automatically parse frontmatter and sync the DB index after writing — no separate `sync_index` call needed.

`delete_doc` reads the file first to detect `foreshadow` type documents, then cleans up `foreshadow_index` alongside `document_index`.

### Delete Approval Protocol

Sub-agents (worldbuilder, character_designer, outliner, director, writer, script_supervisor) can SEE `delete_doc` in their tool list, but cannot EXECUTE it directly. Two layers enforce this:

1. **System Prompt** (`agents.ts` `createAgent`): Sub-agent prompts are appended with a "删除审批协议" section instructing them to declare delete requests with file path + reason + context, rather than calling `delete_doc`.

2. **`beforeToolCall` hook** (`agents.ts`): For all agents except `chief_editor`, the pi Agent's `beforeToolCall` hook intercepts `delete_doc` calls and returns `{ block: true, reason: "..." }`. The framework injects the reason as an error tool result, and the sub-agent naturally includes the delete request in its output.

The Chief Editor (who has no restriction) reads the sub-agent's output via `delegate_to_agent`, evaluates the request, and calls `delete_doc` if approved.

### LLM Configuration

`LLM_PROVIDER` and `LLM_MODEL` provide the default provider/model (`deepseek`/`deepseek-flash` in the pi-ai 1.x builtin catalog; production runs `opencode`/`deepseek-v4-flash-free` via the dynamic runtime catalog). Runtime selection is resolved dynamically through the model resolver and may be overridden per request. All seven Agent configs use `thinkingLevel: "medium"`.

## Key Conventions

- The `packages/novel-agents/` code uses ESM (`"type": "module"`) with `.js` extension in imports
- Pi runtime dependencies are pinned npm packages; a local `pi/` checkout is not required
- YAML frontmatter parsing uses a custom minimal parser in `lib/frontmatter.ts` (not a library)
- `countWords()` handles mixed Chinese + English text
- DB table names use the `novel.` schema prefix in InsForge API calls
- Environment variables are in `packages/novel-agents/.env` (gitignored)

## Skill System

Novel Vibe supports a deliberately restricted profile of the [Agent Skills](https://agentskills.io) standard. A Skill is exactly one `SKILL.md` file with only `name` and `description` frontmatter. Bundled scripts, references, assets, archives, GitHub installation, arbitrary code execution, dependency installation, and user-defined tools are rejected.

### Loading Model

1. **Metadata (name + description)** — always in agent prompt via `formatSkillsForSystemPrompt()` — lists available skills as an `<available_skills>` XML block
2. **SKILL.md body** — loaded on demand via the `load_skill` agent tool when a task matches the skill's description

User Skills can be created only by uploading/pasting `SKILL.md` on `/skills` or by invoking the official `/skill-creator` command in Chief Editor chat. Both paths create a draft, run deterministic and isolated semantic review, show any revision to the user, and require explicit confirmation before installation.

### Storage

Confirmed user Skills are stored in the `skills` bucket at `users/{user_id}/{slug}/SKILL.md`. Agent Prompts and built-in Skills use immutable files in the private `agent-resources` bucket, selected by `public.agent_resources.active_version_id`; bundled files remain bootstrap inputs and optional emergency fallbacks. Drafts and review records remain in PostgreSQL until confirmation.

### Auth for Storage Operations

InsForge has three auth levels for storage API:

| Auth type | Source | Storage access |
|-----------|--------|---------------|
| User JWT | InsForge login → `accessToken` | ✅ Read + Write to `novels` bucket |
| InsForge API Key | `.env` `INSFORGE_ACCESS_KEY` | ❌ Does NOT work for storage API |
| PG JWT (postgres role) | DbClient generates from `JWT_SECRET` | ✅ Full access for trusted workers |

Agent tools use the authenticated user's JWT for RLS-protected Storage. System workers use the PG JWT only for trusted background operations.

### DB Tables

| Table | Schema | Purpose |
|-------|--------|---------|
| `skill_registry` | `public` | Global skill catalog (slug, name, description, storage_path, source) |
| `workspace_skills` | `public` | Per-workspace enable/disable toggle (workspace_id, skill_slug, enabled) |
| `skill_drafts` | `public` | Owner-scoped uploaded/generated candidates and lifecycle state |
| `skill_reviews` | `public` | Immutable policy/model review records and approved content hashes |
| `skill_roles` | `public` | Application-owned Agent role assignments |

Both tables use `Accept-Profile: public` in PostgREST queries (not the default `novel` profile).

### Built-in Skills

Defined by the code-owned allowlist in `lib/agent-resources/catalog.ts`. Source files live at `builtin/{slug}/SKILL.md` for bootstrap/fallback, while normal runtime content resolves from the private `agent-resources` bucket. Currently includes:

- **`skill-creator`** — Official single-file Skill creation workflow, available only through structured `/skill-creator` invocation in Chief Editor chat.

`installBuiltInSkills()` runs on `NovelOrchestrator.init()`, idempotently registers verified built-in resources with `source="built-in"` and `user_id=null`, and auto-enables newly registered defaults for the current workspace.

### Prompt and Built-in Skill Resource Operations

Platform resources are administered explicitly; seeding is not part of normal startup or deployment. Set `AGENT_RESOURCE_FALLBACK_ENABLED=true` only when packaged emergency fallback is desired.

```bash
npm --workspace @novel-vibe/agents run resources -- seed
npm --workspace @novel-vibe/agents run resources -- verify
npm --workspace @novel-vibe/agents run resources -- publish prompt writer ./writer.md --note "reason"
npm --workspace @novel-vibe/agents run resources -- rollback prompt writer 1
```

### Agent Tools for Skills

| Tool | Purpose |
|------|---------|
| `load_skill(slug)` | Loads an enabled, approved, role-compatible Skill after policy and hash verification |
| `create_skill_draft(slug, content, roles)` | Chief Editor only: stores `/skill-creator` output as an uninstalled review draft |

All six Agents have `load_skill`, but each role receives only Skills assigned to it. Runtime loading independently checks workspace enablement, review status, policy version, required capabilities, and SHA-256 content hash. Skill instructions never expand the configured tool allowlist.

### InsForge Development Skills

The InsForge repo contains its own skill set at `InsForge/.agents/skills/insforge-dev/` for platform maintainers. The **backend** skill (`backend/SKILL.md`) is particularly useful — it documents RLS patterns, `withUserContext`, migration conventions, and storage service internals. Use this when debugging InsForge storage/auth issues.

## 逆熵精简机制（Entropy Reduction）

每月一次"精简日"，对设计过度与重复建设做减法。这是**常设治理节奏**（不是一次性活动）：节奏与当期状态记录在 `ROADMAP.md`；完整流程与月度报告（`docs/entropy/**`）保存在**私有运维仓**，本仓只保留生成器 `scripts/entropy-report.sh`。

```bash
./scripts/entropy-report.sh          # 生成月度报告：churn / 体积 / LOC / 死代码
                                     # 默认落盘到私有运维仓的报告目录；--stdout 只打印不落盘
```

核心规则：

- **精简 PR 只做减法**，不混入行为变更或新功能；相关包 `npm run check:*` 必须全绿
- **删产品代码与删测试行数比接近 1:1**，否则是删了覆盖或留了死测试（纯 API 面收窄/de-export 不适用此比率，须在精简记录中注明）
- **正确性敏感区默认不动**：Session 持久化、计费、删除审批协议
- **删不动的记入"待精简清单"**（当月报告内），下月再看，不强删
- 高 churn（长期变动最频繁的文件）与长期霸榜的巨型文件是每次报告的重点观察对象
- **熵减机制本身的故障当月修**（如报告脚本、knip 配置失效）——治理工具不可用时精简日不成立
- 精简中发现的结构性结论回灌 `ROADMAP.md` 或对应 spec；涉及治理规则的变更走 `governance(<scope>)` 提交
